Summary

Every named gap from the first audit got real work. Nothing is fully missing anymore — what's left is depth and polish.

The first audit's top finding was that a second, richer pipeline existed in the codebase but was never wired to a live route. That's no longer true: the keyword-only router was replaced with a real Gemini planner that decomposes a query into a set of agents, multi-turn memory is live end-to-end (backend store and frontend session persistence), language/persona detection now actually reaches the response, lightning/cyclone alerts exist, routing is genuinely hazard-aware, and a brand-new "regional" agent answers the one query type the platform previously couldn't touch at all — "which regions look favorable" — by ranking today's real INCOIS PFZ zones with the already-trained ML classifier.

Two things are worth flagging plainly. First, this session's own new code shipped a real bug — the ML model loader wasn't thread-safe, so the new concurrent regional scan silently returned "unavailable" confidence for most zones until it was caught and fixed (a genuine race condition, not a hypothetical one — reproduced and verified). Second, there is currently no .env file in this checkout, so every advisory tested here was generated by the deterministic, non-LLM fallback formatter, not Gemini's actual persona/language prose. The grounding and localization code is real and tested in isolation, but a live demo without a configured key will look flatter than the code is capable of.

A bug this session shipped, and caught

The regional scan's own concurrency exposed a real race condition

Making per-zone lookups concurrent (via a thread pool, since each is an independent network call) is what makes the regional scan fast enough to be usable. But pfz_ml.py's model loader used a "load once, cache globally" pattern that was never written to be called from multiple threads at once. Under real concurrent load, 7 of 8 threads got None back instead of the trained model — not because the model was broken, but because one thread had flagged "loading started" before it had actually finished assigning the loaded object, and a second thread read that flag and returned early.

This was caught by actually running the new code under a thread pool and inspecting per-thread results, not by inspection alone — the first fix attempt (a naive lock) still had the same bug, because the flag was still being set before the load completed. The corrected version only marks loading "done" after the model is fully assigned, both inside the lock. Re-verified with 8 concurrent callers all getting the real model.

app/pfz_ml.py _get_model() — double-checked locking, flag set only after assignment
Verified via a standalone ThreadPoolExecutor(max_workers=8) test against the live function

Where to spend effort next

Ranked by leverage, now that nothing is fully missing

1
Configure a real Gemini API key before any demo

There is currently no .env in this checkout. Every response tested this round came from the deterministic fallback formatter ("ORCA's AI summarizer is temporarily busy"), not the actual persona/language-aware prose the grounding work was built for. This is the single highest-leverage non-code fix available.

2
Parallelize agent dispatch and remove the duplicate fetches

dispatch_node's agent loop still runs one agent at a time, and main.py separately re-fetches boundary/ocean/PFZ/chlorophyll/hazard data a second time for telemetry — on top of whatever the graph's agents already fetched. Measured: a single query took 23+ seconds. These are independent I/O calls; a thread pool (the same pattern regional_scan.py already uses, lock included) would cut this substantially.

3
Surface historical charts and regional rankings visually

Both are computed with real data but only reach the user as text. Add plot_url to the /api/orchestrate response and render it with an <img>; plot the regional scan's ranked zones as map markers instead of only listing them in the advisory card.

4
Decide how to label PFZ/chlorophyll for a "tomorrow" query

Wave/weather/hazard are now genuinely forecast-aware, but PFZ and chlorophyll intentionally stay "today only" (no free forecast product exists for either). A "tomorrow morning" answer currently mixes a real forecast with today's PFZ data silently — worth an explicit note in the advisory so it doesn't read as inconsistent.

5
Move from route heuristic to real optimization

The current 2-candidate detour is honest about what it is, but a real cost-grid search (even a simple A*) around known MPA/high-wave cells would be a materially stronger answer to the brief's "route optimization" language.

6
Retrain or re-pin the PFZ ML model

The model loads with a live sklearn version-skew warning (trained on 1.9.0, running on 1.8.0). Harmless in every test run so far, but a dependency-mismatch risk worth closing before it isn't.
